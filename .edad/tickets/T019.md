## Context

An evidence record says which commit of the *target* it judged, which decisions the
passing tests discharge, and that those tests were proven capable of failing. It does
not say which harness did the judging. Until T018 that was moot: there was one checkout
of the harness, on the operator's machine. Now a teammate installs it by tag, a
developer installs a checkout editable, and this repo gates itself from an uninstalled
tree — three harnesses that can differ, and every record they write looks the same.
The gate's thesis is that a verdict is a property of the commit and not of what was
installed that day; it enforces that for pytest, ruff and PyYAML through
`requirements-gate.txt`, and is silent about itself. The pin check is one step down in
the same position: `gate_toolchain_problems` measures the versions through
`_probe_versions` before every run, refuses a mismatch, and throws the measurement away.

What the harness can learn about itself depends on how it was installed. A `git+…@v0.1.0`
install has a `direct_url.json` with `vcs_info.commit_id`. An editable install reports
`version` `0.1.0` whatever commit is checked out, with `direct_url.json` `dir_info.editable`
pointing at the checkout. An uninstalled checkout has no metadata — except that a
gitignored `edad_harness.egg-info/` left by any earlier `pip install -e` still answers
`0.1.0` from the cwd, so a version read without a `direct_url` to vouch for it is not an
identity.

The stubs are already in `edad/gate.py`, and they return the wrong shape rather than
raise, so every test in the frozen file fails on its own assertion: `identify_harness`,
`harness_identity` and `toolchain_versions` return `{}`; `harness_metadata`,
`harness_checkout`, `harness_head` and `harness_dirty` return `None`s. `Record` already
carries `harness` and `toolchain` fields defaulting to `{}`, in the right position;
nothing populates them. `tests/test_session_queue.py` is frozen because its exact
key-set assertion on `as_log()` was amended before approval to include `"harness"` —
`test_the_logless_breaker_is_recorded_as_a_breaker_not_a_failure` is red at base for
exactly that reason and goes green with D5.

Two things the suite does that are not yours to fix. `tests/test_session_queue.py`
runs `git` against real temporary repositories, and
`test_run_log_is_gitignored_telemetry` shells to `git check-ignore`; under
`--sandbox docker` git does not work inside the container, by design, so those tests
fail when you run the full suite yourself and pass for the verifier, which runs on the
host. That failure is an environment artifact, not yours, and not to be worked around.
Nothing in `acceptance` shells to git.

## Goal

Every artifact the harness writes names the harness that wrote it. The evidence record
and the approval lock carry a `harness` block — version, commit, dirty, source — and a
`toolchain` block with the versions the pin check actually measured. The session log
and the run log carry the `harness` block beside the fields that already say how a run
was made. Nothing refuses to run on account of any of this: a harness that cannot
identify itself says `unknown`. QUICKSTART says how a release is cut, and the pins
file's header says what a bump actually means.

## Required interface

All of it is pinned by `tests/test_harness_identity.py`; read it first. Names are
exact, because the tests import and monkeypatch them on the `edad.gate` module.

**`edad/gate.py`** — replace the seven stubs beside `gate_toolchain_problems`. Keep
them as module-level functions with these names; the D2 test replaces each seam by
name.

- `identify_harness(version, direct_url, head, dirty) -> dict` — pure. Returns exactly
  `{"version", "commit", "dirty", "source"}`. Rules, in order:
  - `direct_url` has `vcs_info` → `source: "vcs"`, `commit` from
    `vcs_info["commit_id"]`, `dirty: None` (there is no checkout to measure),
    `version` as given.
  - `direct_url` has `dir_info` with `editable` true → `source: "editable"`,
    `commit: head`, `dirty: dirty`, `version` as given.
  - no `direct_url` but a `head` → `source: "checkout"`, `commit: head`,
    `dirty: dirty`, `version: None` — a version with no `direct_url` behind it is a
    stale label, not an identity.
  - otherwise → `source: "unknown"`, everything else `None`.
- `harness_metadata() -> tuple[str | None, dict | None]` — `(version, direct_url)`
  for the `edad-harness` distribution via `importlib.metadata`: the version, and
  `direct_url.json` parsed, `None` where absent. May raise; the gatherer catches.
- `harness_checkout() -> Path | None` — `Path(edad.__file__).resolve().parents[1]`
  when a `.git` exists there, else `None`.
- `harness_head(checkout: Path) -> str | None` — `git rev-parse HEAD` in `checkout`.
- `harness_dirty(checkout: Path) -> bool | None` — whether
  `git status --porcelain --untracked-files=no` in `checkout` prints anything.
- `harness_identity() -> dict` — calls the four above, catches `Exception` from each
  independently (a broken metadata read must not stop git from being asked, and vice
  versa), treats a failure as `None`, and returns `identify_harness(...)`. Never
  raises.
- `toolchain_versions(root: Path) -> dict` — `{name: measured | None}` for every `==`
  line in `root / "requirements-gate.txt"`, in file order, `{}` when the file is
  absent. `measured` is the same value the pin check compares: `meta or on_path` from
  one `_probe_versions(root, name)` call per name. Rewrite `gate_toolchain_problems`
  so the two share that one pass over the file and that one probe per name — the
  test counts probe calls — with its messages and behaviour unchanged.
- `evaluate()`: populate `rec.harness = harness_identity()` and
  `rec.toolchain = toolchain_versions(root)` where `rec = Record(...)` is built. Call
  the module-level names (not a cached value), since the tests patch them.
- `cmd_approve()`: the lock's `_edad` block gains `"harness": harness_identity()` and
  `"toolchain": toolchain_versions(root)`, beside `full_gate_baseline`.
- `write_record` needs no change: `asdict(rec)` already carries the two fields, after
  `uncomparable_failures`.

**`edad/session.py`** — `SessionLog` gains `harness: dict = field(default_factory=dict)`
immediately after `permissions`. Populate it where the log is built, one line beside
`permissions=`: `harness=harness_identity()`, imported from `edad.gate`. No toolchain
in the log.

**`edad/session_queue.py`** — `RunState.__init__` gains `harness: dict | None = None`
after `network`, stored as `{}` when `None`; `as_log()` emits `"harness"` immediately
after `"network"`. Pass `harness=harness_identity()` where `RunState(...)` is built
in the run entry point. No toolchain in the log.

**`QUICKSTART.md`** — add a `## Releasing` section (a top-level `## ` heading, the
literal text `Releasing`). The test reads the section up to the next `## ` heading and
requires it to mention `pyproject.toml`, `git tag` and `git push`. The procedure it
documents: one commit bumps `version` in `pyproject.toml` and the pinned install line
in this file (`test_quickstart_pinned_tag_matches_project_version` forces them to
agree), merged by pull request, tagged `vX.Y.Z` on the merge commit, tag pushed.
Nothing is bumped per ticket; commits between releases are identified in records by
`harness.commit`. Wording is yours, in the file's register.

**`requirements-gate.txt`** — reword the header comment. It currently says bumping a
pin invalidates prior evidence; it does not. Each record stays valid for its commit,
because the check guaranteed the pins at that commit and from this ticket on the
record says which they were. A bump means *new* records are made under different
pins. (D8; unenforced — a comment.)

## Out of scope

- **Pinning the harness in a target's pins file** so the gate refuses a mismatch.
  Deferred until ai-sniffer has run some nights and a real harness upgrade has
  happened.
- **The pytest 8.4.2 → 9.0.3 bump.** Its own ticket, after a probe that 9.0.3 still
  emits the lines the gate's pytest parsers match.
- **Toolchain in the logs.** Record and lock only.
- **A warning on a dirty checkout at run time.** Record-only says no.
- **Placing and pushing the release tag** (D7). An operator act the gate cannot see.
- **Backfilling old records or locks.** They lack the keys; a reader treats absence
  as unknown. A backfilled value would be the record asserting something the gate
  never measured.
