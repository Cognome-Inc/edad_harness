## Context

D1's loop of three rounds spans several invocations (D27). A CLI cannot call
back into the ticket-writing session that launched it. So each `python3 -m
edad.review tests <T>` runs exactly one round:

- it launches one fresh reviewer, built by T030's builders;
- it appends the round to `.edad/hashes/<T>.review.json`, in the shape T029's
  `review_problems` reads;
- on a pass, it runs `gate approve` itself.

Between rounds the writer revises the tests, or disputes a finding with
`--dispute F3="reason"` (repeatable), and runs the command again. The next
reviewer rules on each dispute.

These rules come from D1, D9 and D27:

- A round passes when no security, blocker or major finding remains. D9 says
  "blocker or major". Security ranks above blocker in D14, so it fails a round
  too.
- Reviewer output that does not match the expected structure counts as a
  failed round.
- A fourth round is refused.
- The counter resets only when `approve-criteria` is re-run over *changed*
  criteria, so a stuck ticket comes back through a person.

**Narrowed decision.** D1's line says "looping up to 3 rounds". D27 narrows
that: the loop spans invocations, one round each.

**Amended verify (authoring, before approval).** D27's verify named two tests.
The hand-run test review found that the dispute refusal, the reviewer's inputs,
the real approve runner and a crashed reviewer were each specified here but
untested. Four tests were added and D27's verify in the spec and grill now
names all six, as T030 did for D5.

**Hand-run test review.** `edad.review tests` is what this ticket builds, so
its own tests were reviewed by hand: seven rounds, each by a fresh reviewer that
had seen neither the writer's reasoning nor an earlier round's findings. The
serious findings per round were 8, 6, 5, 2, 1, 2 and 3. Each was fixed and
checked against a list of deliberate mutations of a throwaway implementation;
the tests catch 62 of 63. The survivor drops the stale-criteria refusal, which
is marked "recommended, not tested" below. The operator chose to stop after
round 7 and approve with the override.

**How the tests reach the round (seam S5).** The tests drive `review.main()`
with `sys.argv`, so the parser and `--dispute` are under test. They replace the
two names that would launch a process, `review.run_reviewer` and
`review.run_approve`, and make any other `subprocess.run` or `Popen` call fail
the test. The repo is a temp directory reached through `EDAD_REPO`, so find the
root with `gate.repo_root()`, which honours it, and not with git. The fake
approve writes the lock as the real one does. No test launches a model or a
gate, and none shells to git, so the suite behaves the same inside the agent
container.

**The test file is shared with T030.** T030's two tests in
`tests/test_test_review.py` are unchanged; only the module docstring and the
imports changed. T030's lock over this file is therefore stale. That is
expected, since nothing re-checks a done ticket's lock.

**Constraint from T030's frozen tests.** `review_prompt` is shared with the
panel. Its framing (everything but the three inputs) is capped at 600
characters when no disputes are passed, and a prompt built from one rubric may
carry no other rubric's ids. So the output-format instruction must not use item
ids as examples: write `"item": <rubric item id>`, not `"item": "T2"`. The
probe's instruction took the framing from 196 to 318 characters. Disputes
reach the prompt as a keyword-only parameter with a default.

## Required interface

`edad/review.py` lands with returning stubs, `run_reviewer` and `run_approve`,
and with `--dispute` already in the parser. Each frozen test goes red on its
assertion. Replace the bodies; keep the names, signatures and parser.

- **`run_reviewer(argv: list[str]) -> str`** launches the reviewer with
  `subprocess.run(..., capture_output=True, text=True)` and returns its stdout. When the process exits non-zero, refuse through `gate.die()`
  with no round recorded. A reviewer that never ran has not judged anything,
  and must not use up one of the three rounds.
- **`run_approve(root: Path, ticket_id: str) -> int`** runs `[sys.executable,
  "-m", "edad.gate", "approve", ticket_id]` through `subprocess.run` with
  `cwd=root`, and returns its exit code.
- **`cmd_tests(args)`** runs one round. It calls the two runners above by their
  module names, so the tests' replacements are the ones used.
  - **Exit codes:** 0 when the round passes and approve returns 0; approve's
    own exit code when the round passes and approve fails; 1 when the round
    fails, malformed output included; 2 (through `gate.die()`) for a refused
    invocation, which launches nothing and writes nothing.
  - **Refused:** a fourth round under the same approved criteria. The message
    names `approve-criteria`, the only way out. Also refuse a `--dispute` that
    is not `F<n>=<reason>` with a reason that is not blank, that names no
    finding of the last round, or that comes before any round has run.
  - **Recommended, not tested:** also refuse when the criteria record is
    missing, or no longer matches `gate.criteria_sha256(ticket)`. Approve would
    refuse that ticket anyway, so the round would be wasted.
- **The prompt.** The spec is the ticket's `spec:` file. The artifact is every
  frozen file's text, each under a header naming its path. The rubric is
  `load_rubric("tests")`. Disputes, when given, follow the rubric: each
  disputed finding's item, severity and issue, then the writer's reason.
- **`reviewer_argv`** also passes `--tools ""`, which switches off every
  `claude` tool. The prompt is then all the reviewer can read: no CLAUDE.md
  in the repo, no files, no shell. This closes T030's open item. T030's argv
  test still holds: `claude -p` comes first, the prompt appears once, and
  there is no resume flag.
- **Reviewer output.** A well-formed output, after stripping whitespace and at
  most one surrounding Markdown code fence (```` ```json ```` or ```` ``` ````),
  is a JSON object whose `"findings"` is a list. Each finding is an object with
  a string `"item"`, a string `"issue"`, and a `"severity"` that is one of
  `"security"`, `"blocker"`, `"major"` or `"nit"`. Extra keys are allowed,
  on the object and on each finding. Anything else is malformed.
- **Order.** Write the round to the record *before* calling approve. The real
  approve reads that record, and refuses a pass it cannot see yet.
- **Finding ids** are `F1`, `F2`, … in the order the reviewer printed them,
  numbered per round. `--dispute F<n>=reason` names a finding of the most
  recent round.
- **Review record** `.edad/hashes/<T>.review.json`, written with
  `gate.write_hash_record` and read with `gate.read_record`. Each invocation
  appends one round and never rewrites the earlier ones:

  ```
  {"rounds": [{"round": <1..3 under these criteria>,
               "verdict": "pass" | "fail",
               "model": <the --model value in the argv, or null>,
               "frozen": {"<frozen path>": "<sha256>"},   # gate.frozen_hashes_now
               "criteria": "<sha256 from the criteria record>",
               "findings": [{"id": "F1", "item": ..., "severity": ..., "issue": ...}],
               "disputes": [{"id": "F2", "finding": {...}, "reason": "..."}]}]}
  ```

  `round`, `verdict`, `model`, `frozen` and `findings` are the fields T029
  fixed. `disputes` holds the disputes this round's reviewer was given, each
  with the finding as the last round recorded it. Extra fields, such as a
  timestamp or a malformed flag, are welcome and untested. `criteria` is what makes the counter work. `approve-criteria` keeps
  no fingerprint history, so each round stores the fingerprint it ran under.
  The rounds that count are the ones whose `criteria` equals the criteria
  record's current `sha256`. Re-approving the same criteria writes the same
  sha256, so nothing resets. Editing the criteria without approval leaves the
  record's sha256 where it was, so nothing resets either.
- **Output (untested; wording is cheap to tune).** Print the round number, the
  verdict and each finding with its id, so the writer can dispute by id.

`.claude/skills/to-tickets/SKILL.md` gains the daytime flow:

1. Ask the operator to run `approve-criteria <T>` at a terminal.
2. Run `python3 -m edad.review tests <T>` once per round.
3. On a failed round, revise the tests or dispute findings by id, then run it
   again.
4. After three failed rounds, change the ticket and ask the operator for
   `approve-criteria` again, or for `override-review`.

The skill's existing step, "confirm with the user before running `edad.gate
approve`", becomes "confirm before asking the operator for approve-criteria".
A passing round runs approve itself.

## Out of scope

- The panel: T034–T036.
- The model pin: T034. This ticket's reviewer gets it through the shared
  builder once T034 merges, and the record's `model` follows from the argv.
- Deleting the review record does reset the counter. D27 rejects deletion *as
  the reset mechanism*. Nothing here can detect a deleted file without reading
  git history. The record is committed, so a deletion shows in the diff a
  person merges.
- The prompt travels as one argv element. Linux caps a single argument at
  128 KiB (macOS caps only the total). The daytime review runs on the host, and
  this spec's largest prompt is about 58 KB (spec 42 KB, tests 16 KB). Moving
  the prompt to stdin is a later ticket if a spec outgrows that.
