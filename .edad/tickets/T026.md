## Context

`evaluate(root, ticket, gate_name, base_ref)` in `edad/gate.py` is the one entry
point for a verdict; the CLI (`python3 -m edad.gate run T --base-ref REF`) and the
session controller both call it. It uses `base_ref` three times and checks it
nowhere: `die_on_toolchain_mismatch` asks `changed_files(root, base_ref)` whether
the pins changed since it, `trusted_input_problems` runs `git show
<base_ref>:<lock>` to compare the approval lock at it, and `rec.changed_files =
changed_files(root, base_ref)` diffs against it.

A ref that does not resolve, or one that resolves but shares no history with HEAD
(an orphan commit), makes `git diff <ref>...HEAD` exit 128 inside `changed_files`,
where `git()` runs with `check=True` - and the operator gets a bare
`subprocess.CalledProcessError` traceback, exit code 1, instead of the gate's own
refusal. Before the crash, `trusted_input_problems` swallows the same git error and
reports "approval lock modified since <ref>" - a false verdict about the agent.
With a mismatched toolchain the crash arrives earlier, from the refusal's pins
check; that is how T023's review met it, but the toolchain is not the cause.

The session controller passes `git rev-parse HEAD` of the checkout, which is always
an ancestor of the worktree's HEAD; the queue passes no ref. Nights never hit this.
It is the operator's hand-run gate that does.

**Your container has no git.** Every test in the frozen file builds a real
temporary repository and one spawns `python3 -m edad.gate` in it, so all eight fail
where you run them; the verifier on the host runs them for real. The check you are
adding is a git call, which is why the tests do not fake git. Do not work around
this. Confirm your change by reading the frozen file and reasoning about it, and by
running the rest of the suite, which does pass in-container apart from the tests
elsewhere that also shell to git.

**Three frozen suites fake `gate.git`.** `tests/test_gate_refusal.py` (T021) and
`tests/test_refused_iteration.py` (T023) replace `gate.git` with a function that
answers a constant for every call and run the real `evaluate` against a directory
that is not a repository, with a made-up base ref. They run under `full_gate`. A
probe that reaches git any other way - `subprocess.run` directly, `_git_answer`,
`git_raw` - meets real git there, refuses, and turns eight of their tests red. The
D3 test in your frozen file catches the same thing from the other side: it wraps
the real `gate.git` to fail only for `merge-base` on a valid ref, and only a probe
routed through `gate.git` sees that failure.

## Goal

When `evaluate` is given a base ref, the first thing it does with it is ask git
for the merge base of that ref and HEAD, through the module's own `git()` helper.
If git cannot answer - the ref does not resolve, or there is no merge base - it
refuses through `die()`, naming the ref as it was given, before the toolchain is
measured, before the lock is compared, before anything is diffed. No `Record` is
built. A ref that is an ancestor of HEAD evaluates exactly as today; no ref means
no probe.

## Required interface

The frozen tests assert these; neither side can change them.

**`evaluate(root, ticket, gate_name="acceptance", base_ref=None)`** - unchanged
signature. With a `base_ref` that git cannot find a merge base for against HEAD,
it raises `gate.Refusal` (the type `die()` raises: a `SystemExit` with `code == 2`
and a `.reason`) whose reason contains `base_ref` verbatim, and does so before
`measure_toolchain` is called and before any `git diff` or `git show` (D1, D2,
D4). The reason never contains "approval lock modified" (D5). With a `base_ref`
that is an ancestor of HEAD it returns a `Record` with `base_ref` set, having
called `gate.git(root, "merge-base", ...)` exactly once; with `base_ref=None` it
returns a `Record` having made no `merge-base` call (D6).

**The probe is `git(root, "merge-base", base_ref, "HEAD")`** - the module-level
`git` helper, looked up at call time so a test can replace it - with
`subprocess.CalledProcessError` caught and turned into the refusal (D3). Nothing
else is added to `evaluate`'s git traffic.

**The CLI** `python3 -m edad.gate run <ticket> --base-ref <bad>` exits 2, prints
`edad: <reason>` with the ref on stderr, and prints no `Traceback` on either
stream (D5). This is `die()`'s existing behaviour once the refusal is raised;
nothing in `cmd_run` or `main` needs to change.

Wording of the reason is yours. The tests pin that the ref is named, not the
sentence around it; one message for both failure kinds is fine, and so is
splitting on git's exit code (128 for a name that does not resolve, 1 for no merge
base) if you prefer.

## Out of scope

- `trusted_input_problems` keeps swallowing git errors on `git show
  <ref>:<lock>`: after the guard, a failure there can only mean the lock is absent
  at base, which is what the code already takes it to mean (D8, unenforced).
- The evidence record keeps `base_ref` as given, not resolved to a SHA (D8).
- `--base` keeps working as argparse's abbreviation of `--base-ref` (D8).
- Not-a-repository and git-not-installed are untouched: pre-existing, and
  unreachable from the CLI, which resolves its root through git first (D8).
- The existing frozen suites that fake `gate.git` are not in this ticket's
  `frozen` list; they hold the line under `full_gate` (D3's amendment in the spec).
