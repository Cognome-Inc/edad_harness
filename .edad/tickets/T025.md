## Context

`run_session` (`edad/session.py`) runs the ticket's `acceptance` commands after
every agent iteration and retries a failure with `retry_prompt`. The `full_gate`
commands run **once**, after the loop, and `full_gate_failure` sorts a failure
there into `Unwinnable` (a frozen file is named), `Abort` (the baseline could not
be applied), `Abort` ("failures this ticket introduced"), or a fall-through
`Abort`. All four end the night. Three nights — T020, T024 nights 1 and 4 — ended
on the third kind: one ruff finding in the agent's own new code, acceptance fully
green, and the finished branch discarded because a re-run starts from the approval
lock. Each was recovered by a manual re-run that passed first time.

The agent was never told the full gate exists. `initial_prompt` lists only the
`acceptance` commands and says "you are done when these commands exit 0";
`full_gate` reaches the agent only through `allowed_tools`, which is what it may
run, not what it is asked to run. The lost nights were not disobedience.

**The stubs.** The tree already contains a `full_gate_retry_prompt` that returns an
empty string and an `Iteration.full_gate` field defaulting to the string `"stub"`.
They exist so the frozen tests reach their assertions and fail there rather than
on an import. Replace them; do not build on them.

**`Iteration` is constructed positionally.** The loop builds it as
`Iteration(n, exit_code, commit, rec.passed, sig, violations, made_commit, out)`,
and `tests/test_refused_iteration.py` (frozen for T023) reads `agent_output` by
name from that construction. Keep `full_gate` the last field, after
`agent_output`, or construct by keyword; a field inserted earlier shifts the
positional call and turns the agent's output into the full-gate verdict.

**A green `Record` has a truthy signature.** `failure_signature` on a record with
no failures returns a constant hash of empty output. Today that never repeats,
because a green iteration ends the loop; with retries, three green-acceptance
iterations in a row would carry the same signature and `check_kills` would end the
night for passing. D4 says what a green-acceptance iteration contributes instead.
Do not change `failure_signature` itself: the acceptance path keeps it.

**Only failures naming a frozen file are unwinnable.** `frozen_blocks`
(`edad/gate.py`) classifies nothing else; an introduced failure naming a file
outside the ticket's scope but not frozen is "introduced" and is retried like any
other. If the agent cannot clear it from scope, the same keys repeat and the
repeat kill ends the night with the keys in the reason.

**Your container has no docker and no git.** The frozen file for this ticket
shells to neither: every side effect of the loop is replaced. Tests elsewhere in
the suite that do shell to git fail in-container and pass for the verifier on the
host; that is the environment, not your defect, and not something to work around.

## Goal

Once an iteration's acceptance commands pass, the full gate runs in that same
iteration. A failure the ticket introduced sends the agent round again with the
verifier's output and a prompt that says acceptance passed; a failure that no
permitted edit clears, or one the baseline cannot compare, ends the night as it
does today. The retry spends an iteration under the ticket's `max_iterations` and
the same kill conditions, the log records what the full gate found without
changing what `gate_passed` means, and the agent is told from the start that the
full gate exists and what it will run.

## Required interface

The frozen tests assert these; neither side can change them.

**`initial_prompt(ticket, sandbox="none", network=None) -> str`** — unchanged
signature. Its text contains every `ticket["full_gate"]` command verbatim, each
appearing after the acceptance commands; the word `baseline`; and one of the words
`changed`, `touched` or `modified` in the rule that findings in files the agent
changed are the agent's to clear. Wording is otherwise yours (D1).

**`full_gate_retry_prompt(ticket, rec, iteration, sandbox="none", network=None) -> str`**
— a new builder beside `retry_prompt`, with the same positional order. Its text
contains the ticket id, the words `acceptance` and `pass`, the word `frozen`,
`network_rule(sandbox, network=network)`, and for every failing command in
`rec.commands` a `$ <command>` line followed by that command's `output_tail` (the
killed-command treatment `retry_prompt.describe` gives is expected here too).
Passing commands are not quoted. The loop hands this prompt, called as
`full_gate_retry_prompt(ticket, full, n, args.sandbox, args.network)`, to the next
agent run after an introduced failure (D6).

**The loop.** `evaluate(wt, ticket, "full_gate", base)` runs in an iteration if
and only if that iteration's acceptance record passed. `write_record` runs for
every record. Outcomes (D2, D3):
- `full.passed` or `full.passed_modulo_baseline`: promote as today; the loop ends.
- `full_gate_failure(ticket, full)` returns `Unwinnable`, or an `Abort` whose
  reason names an uncomparable baseline, or the fall-through `Abort`: raise it,
  as today.
- otherwise ("failures this ticket introduced"): the iteration's signature becomes
  the D4 value, `check_kills` is consulted, and the loop continues with the D6
  prompt.

**The signature a green-acceptance iteration appends** (D4): `"full_gate:"` +
`"|".join(sorted(k for keys in full.new_failures.values() for k in keys))` when
the full gate found introduced failures — e.g. `full_gate:lint:edad/session.py:I001`,
or `full_gate:lint:edad/session.py:E501|lint:edad/session.py:I001` for two — and
`""` when both gates passed. This is what the iteration's `signature` field holds
and what `check_kills` sees. Acceptance failures keep today's signature.

**`Iteration.full_gate: str | None`**, last field, default `None`. `None` when the
full gate did not run in that iteration — acceptance failed, or the full gate was
refused before producing a verdict — and also when the full gate ran and ended the
night as unwinnable or uncomparable, since the abort reason carries that;
`"passed"`, `"passed_modulo_baseline"` or `"introduced"` otherwise. The full-gate record's `violations` are appended to the
iteration's `violations` whenever the full gate ran, including the runs that end
the night. `gate_passed` keeps meaning the acceptance gate passed (D5, D8).

**Exhaustion** (D7): when `max_iterations` runs out and the last iteration passed
acceptance, the abort reason is
`exhausted {N} iterations: acceptance passed, full_gate still failing: ` followed
by `<command> -> <key>, <key>` per introduced command, joined by `; `, in the same
shape `full_gate_failure` already prints. When the last iteration failed
acceptance the reason is unchanged: `exhausted {N} iterations without passing the
gate`.

**The docstring** (D9): the flow line at the top of the module no longer contains
`]xN  ->  full gate  ->  evidence`; the bracket that is repeated `xN` names
`full gate` inside it, e.g.
`worktree -> [ prompt -> agent -> commit -> acceptance -> (full gate) ]xN -> evidence`.
